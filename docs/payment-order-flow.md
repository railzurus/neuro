# ТЗ: оплата (ЮKassa) и выдача аудио

Статус: черновик к реализации. Требует сверки с юристом (раздел «Юридическая часть»)
и с бухгалтером (54-ФЗ, налоги).

## 1. Цель и главный риск

Пользователь оплачивает 299 ₽ и получает MP3 со своей мантрой.

Главный риск, который решает эта схема: **человек оплатил, но не получил файл**
(завис компьютер, пропала сеть, закрыл вкладку, ошибся в почте). Сейчас у сайта
нет серверного состояния, поэтому после сбоя восстановить выдачу нечем.

Решение: после оплаты на сервере живёт **заказ** с параметрами генерации, доступный
по неугадываемому токену. Пользователь может вернуться к нему в любой момент.

## 2. Ключевое архитектурное решение: файл не хранится

Генерация аудио уже сейчас **клиентская**:

- перед синтезом текст проходит техническую подготовку в `api/refine.php`
  (`mode=tts`): ударения, числа прописью, разбивка на фразы, разметка пауз
  `sil<[мс]>` и акцентов `<[accented]>`. Пользователю этот вариант не
  показывается — в интерфейсе и в заказе хранится его собственный текст;
- `api/tts.php` отдаёт только куски синтезированного голоса (SpeechKit v1);
- микс с альфа-волнами и кодирование MP3 (`@breezystack/lamejs`) делает браузер
  в `src/lib/audio.ts` (`prepareForTts` → `synthesizeVoice` → `renderMix` →
  `encodeMp3`).

Сервер MP3 никогда не получает. Поэтому:

- **храним не файл, а параметры** (текст истории + голос + темп) — это килобайты,
  а не мегабайты;
- при повторном заходе файл **генерируется заново** в браузере из тех же параметров;
- отпадает вопрос файлового хранилища, S3, квот диска и retention для аудио.

### Письмо содержит ссылку, а не вложение

Раз сервер не имеет файла, отправить вложением его нельзя без загрузки MP3 с клиента
на сервер. Это лишний шаг, лишнее хранение ПДн и проблемы с размером вложения
и доставляемостью писем.

**Письмо содержит ссылку на страницу заказа `/order/{token}`.** Оттуда пользователь
скачивает файл. Это же решает и проблему «указал не ту почту» — адрес меняется
на самой странице заказа.

> Если бизнес всё же захочет именно вложение — потребуется загрузка сгенерированного
> MP3 с клиента на сервер и транзиентное хранение (минуты, до отправки письма).
> Рекомендация: не делать.

## 3. Поток

```
[/listen] «Купить за 299 ₽»
    ↓  email + подтверждение адреса + PaymentConsentNote
POST /api/order-create.php
    → создаёт заказ (status=pending, token)
    → создаёт платёж в ЮKassa (Idempotence-Key)
    ← { confirmation_url, token }
    ↓
[виджет/redirect ЮKassa]  ←— карта вводится на стороне ЮKassa
    ↓
    ├─→ redirect обратно на /order/{token}
    └─→ POST /api/yookassa-webhook.php (payment.succeeded)
            → перепроверка статуса запросом в API ЮKassa
            → status=paid, запись согласия, отправка письма со ссылкой
    ↓
[/order/{token}]  ← точка восстановления после ЛЮБОГО сбоя
    • «Скачать MP3» (генерация в браузере по параметрам)
    • «Отправить на почту» / «изменить адрес»
```

Восстановление после сбоя: пользователь заново открывает `/order/{token}` (ссылка
пришла на почту) и повторяет скачивание. Файл создаётся заново — «не успел скачать»
лечится в один клик.

## 4. Схема БД (MySQL на Beget)

### `orders`

| Поле | Тип | Описание |
|---|---|---|
| `id` | BIGINT PK | |
| `token` | CHAR(64) UNIQUE | `bin2hex(random_bytes(32))`, публичный идентификатор |
| `payment_id` | VARCHAR(64) UNIQUE | id платежа в ЮKassa |
| `status` | ENUM | `pending` / `paid` / `canceled` / `refunded` |
| `amount` | DECIMAL(10,2) | 299.00 |
| `currency` | CHAR(3) | RUB |
| `email` | VARCHAR(255) | куда слать ссылку и чек |
| `params` | JSON / TEXT | `{ finalText, voice, speed }` — **содержит ПДн**, чистится по сроку |
| `params_purged_at` | DATETIME NULL | когда параметры обнулены |
| `created_at` | DATETIME | |
| `paid_at` | DATETIME NULL | |
| `delivered_at` | DATETIME NULL | когда ушло письмо |
| `expires_at` | DATETIME | дата очистки `params` |

### `consents` — доказуемость согласия (ч. 3 ст. 9 152-ФЗ)

| Поле | Описание |
|---|---|
| `id`, `order_id` | привязка к заказу |
| `email` | кто согласился |
| `doc_versions` | JSON: `{ privacy: '2026-08-03', terms: '...', consent: '...' }` |
| `accepted_at` | точное время |
| `ip`, `user_agent` | контекст |

Именно эта таблица закрывает бремя доказывания: без неё мы можем показать только
«сайт так выглядел», но не «этот человек согласился тогда-то».

### `email_log`

`order_id`, `email`, `sent_at`, `status`, `type` (`delivery` / `resend`).
Нужен для антиабьюза переотправок и разбора жалоб «письмо не пришло».

## 5. Эндпоинты (`api/`, стиль как в `tts.php`)

| Эндпоинт | Метод | Назначение |
|---|---|---|
| `order-create.php` | POST | Создаёт заказ + платёж в ЮKassa. Тело: `{ params, email, consent: true }`. Отдаёт `{ token, confirmation_url }` |
| `yookassa-webhook.php` | POST | Приём уведомления. **Не доверять телу** — перепроверять статус запросом в API по `payment_id` |
| `order.php` | GET | `?token=…` → `{ status, email (маскированный), params }`. Параметры отдаются **только при `status=paid`** |
| `order-email.php` | POST | Переотправка письма / смена адреса. Rate limit |
| `cron/cleanup.php` | cron | Обнуляет `params` у заказов старше `expires_at` |
| `cron/reconcile.php` | cron | Досверка «зависших» `pending` (webhook не дошёл) |

Секреты (shop_id, secret_key ЮKassa) — в `api/config/secrets.php`
(gitignored, `.htaccess` уже закрывает доступ), как ключи Яндекса сейчас.

## 6. Требования к надёжности и безопасности

- **Идемпотентность.** Webhook может прийти несколько раз — повторная обработка
  не должна слать письмо дважды и не должна дублировать заказ.
  При создании платежа передавать `Idempotence-Key`.
- **Не доверять webhook на слово.** Всегда перепроверять статус запросом в API
  ЮKassa. Дополнительно — проверка IP из списка ЮKassa.
- **Токен неугадываемый** — 32 байта энтропии. Доступ к заказу только по нему.
- **Reconcile-cron** — если Beget был недоступен и webhook не дошёл, платёж
  всё равно будет подхвачен (ЮKassa повторяет уведомления, но подстраховка нужна).
- **Rate limit** на `order-email.php` (например 5 отправок в час на заказ), чтобы
  сервис нельзя было использовать как рассыльщик.
- **HTTPS** — уже есть.
- PCI DSS в полном объёме не требуется: карта вводится на стороне ЮKassa (SAQ A).

## 7. Фронтенд

Новые/изменённые маршруты:

- `/listen` — кнопка «Скачать запись (MP3)» заменяется на «Купить за 299 ₽».
  Перед оплатой: поле email + **подтверждение адреса** («отправим на `x@y.ru`, верно?»)
  и уже готовый `PaymentConsentNote` из `src/components/Legal.tsx`.
- `/order/:token` — новая страница: статус оплаты, «Скачать MP3» (регенерация
  через существующий `synthesizeVoice`/`renderMix`), «Отправить на почту»,
  «Изменить адрес». Работает как точка восстановления.

Подтверждение email до оплаты — важный шаг: он отсекает большинство опечаток
заранее (см. крайний случай в §9).

## 8. Сроки хранения (retention)

Два разных срока — это принципиально:

| Что | Срок | Почему |
|---|---|---|
| `params` (**текст истории** — ПДн) | 14 дней после оплаты, затем автоудаление | Окно на перескачивание. Минимизация: дольше не нужно |
| Запись о платеже (без текста): `payment_id`, сумма, дата, email | По требованиям учёта / 54-ФЗ | Бухгалтерия, чеки, возвраты |

После обнуления `params` страница заказа перестаёт генерировать файл — это надо
честно написать в письме («ссылка активна 14 дней»).

## 9. Крайние случаи

| Ситуация | Что происходит |
|---|---|
| Завис компьютер / пропала сеть / закрыл вкладку | Открывает `/order/{token}` из письма, скачивает заново |
| Ошибся в email | Меняет адрес на странице заказа и переотправляет |
| **Потерял и вкладку, и email неверный** | Автоматически не решается. Только поддержка по `payment_id` из банковской выписки/чека. Поэтому подтверждение email до оплаты обязательно |
| Оплата прошла, SpeechKit лежит | Файл не сгенерировать → случай для возврата. Нужна согласованная с юристом политика возврата |
| Webhook не дошёл | Подхватывает `reconcile.php` |
| Двойной webhook | Идемпотентность — письмо уходит один раз |

## 10. Юридическая часть (передать юристу)

**Главное: текущая Политика противоречит этой схеме.** Сейчас в ней написано:

> «Оператор не обрабатывает информацию личного характера, которую Пользователь
> указывает в текстовом виде при использовании Сервиса»

Как только мы сохраняем `params` (текст истории) на сервере — это утверждение
становится неверным. Требуется правка документов:

1. **Убрать/переформулировать** пункт про необработку текста.
2. **Добавить в таблицу целей** строку: цель «оказание услуги (генерация и доставка
   аудио)», данные — «текст, введённый Пользователем; адрес электронной почты;
   идентификаторы платежа», срок — «14 дней с момента оплаты», порядок уничтожения —
   «автоматическое удаление».
3. **Правовое основание** — исполнение договора (не требует отдельного согласия,
   но требует раскрытия в Политике).
4. **Уведомление в РКН** — состав обрабатываемых данных меняется, надо актуализировать.
5. **Политика возврата** (ЗоЗПП) — сейчас в оферте «вознаграждение не подлежит
   возврату»; нужно описать случаи, когда услуга фактически не оказана.
6. **Лог согласий** (`consents`) — техническое исполнение ч. 3 ст. 9 152-ФЗ.

Также в оферте уже есть согласие на получение **чеков в электронной форме по email** —
это согласуется с 54-ФЗ и делает email обязательным реквизитом заказа.

## 11. Что нужно вне кода

Подробности обсуждались отдельно; кратко:

- договор с ЮKassa + прохождение модерации сайта;
- **онлайн-касса и регистрация ККТ в ФНС** (54-ФЗ) — самый долгий пункт;
- система налогообложения и учёт выручки;
- страница оплаты с описанием услуги, ценой, условиями возврата.

Инфраструктура: **новый сервер не нужен**, хватает Beget (PHP + MySQL + cron + HTTPS).
Фискализацию выполняет облачная касса, а не наш сервер.
